# Rolling Budget — Feature Specifications (Staging)

This document records the behavior described in the former README. It is a staging specification, not a release log. For change history see [CHANGELOG](../CHANGELOG.md).

## Expense due days (staging)

Fixed expenses, variable expenses, loans and credit cards use an optional **day of month** (`dueDay`: integer 1–31, or `null` for no due day). Desktop and mobile budget cards offer day selectors instead of free-text fields. Recurring rules derive their nominal due day from the selected Start date; for shorter months, the scheduled occurrence uses the last calendar day (February 28/29, April 30) while retaining the original nominal `dueDay` (for example, 31).

Previously saved text dates such as `1st`, `22nd` and `23th` are displayed through a compatibility reader and converted to integers on the next successful, revision-checked budget save or explicit local/cloud reconciliation. Unrecognized dates are preserved for manual correction, never silently deleted. The staging recurring-rule database migration adds a checked `due_day` column and permits full calendar Start/End dates. The legacy `due` column remains temporarily for compatibility with already deployed clients; new code writes `due_day`. **Production data and schema are not changed by this staging PR.**

## Recurring rules (staging)

The authenticated **Recurring Rules Manager** is available from the main desktop navigation or the mobile sidebar. Rules are shared across budget years. Each rule has a required Start date, an optional End date, and a frequency. Missing occurrences are added automatically to saved, eligible cloud budget years. New budget years receive applicable rules after their first successful cloud save.

Editing amounts or frequency, disabling, and re-enabling rules take effect from the next eligible calendar month. Saved transactions, including previously generated future entries and manual adjustments, are never overwritten or deleted. Consequently, previously generated entries retain their earlier amount even when a rule changes.

Each desktop/mobile manager displays synchronization results and warns about possible duplicate transactions that were skipped. **Retry synchronization** appears when cloud synchronization is incomplete. It re-reads the owner-scoped cloud budget and preserves optimistic revision and local-conflict checks; it does not automatically resolve conflicts or approve possible duplicates. Pending retry ranges are stored in owner-scoped browser storage across tab closes and are retried automatically after the next authenticated sign-in. A failed retry remains visible in the manager, with a manual Retry synchronization action. Resolve a flagged cloud conflict with the existing budget reconciliation controls before retrying. A budget may be successfully cloud-saved while recurring entries remain pending; the budget screen reports this separately without falsely marking the saved budget as unsynced.

The PR build uses isolated Playwright Supabase mocks; the credentialed live staging workflow is restricted to staging `main`, so live authenticated recurring-rule persistence must be independently verified before approving a release.

Budget year selection is available directly above the authenticated budget on desktop and mobile. The current year plus two future years are automatically selectable without creating empty cloud records. Older saved years remain available; unsynced local years are retained for explicit recovery. The Settings menu no longer contains a Budget Years section. A future year is saved on its first edit, after which existing global recurring rules are applied to that saved year.

In a future budget year without manually entered transactions, the desktop and mobile budget views offer **Copy Previous Year’s Plan** when the preceding year has manual planned entries. Confirmation is required. The preceding year must be cloud-saved, conflict-free and verified against its current cloud revision before either planning action is allowed. Generated recurring transactions already present in the target are preserved; exact matching scheduled transactions are not copied again. The action copies manual planned categories and amounts without historical debt balances, and it never overwrites existing manual entries. Cloud sync follows the existing save-on-demand path. If browser storage fails, the change is rolled back and reported as unsaved. If cloud sync fails, the local copy is retained with a reconciliation warning. Reconciling a previously local-only year into the cloud automatically backfills eligible global recurring rules. Cloud recovery validates the downloaded budget, creates a local backup before replacement, and rejects account switches or concurrent local edits.

For cross-year rollover, an empty January opening can optionally use the preceding December's projected ending balance. Desktop and mobile offer a confirmation action; this never automatically changes existing nonzero January opening balances. Negative projections are supported.
